Both were designed/debugged in the consuming project's package cache this session (see that project's gaussian-morphing.session.md/context for full history) because that's what governed runtime behavior there; this port makes them permanent.

- Fix 1 — GC.Alloc source: `ReadFloat`/`WriteFloat`/`WriteUInt` (helper methods used throughout the chunk-bounds computation) each allocated a fresh `byte[4]` via `System.BitConverter` on every call — confirmed via Profiler as the source of 3,770,246 individual GC.Alloc calls inside a single `GaussianSplatMorpher.OnEnable()` at real asset scale. Rewritten to direct bit-shift math (unsafe pointer reinterpret for float↔uint), no heap allocation per call.
- Fix 2 — WarmUpStep (spread Setup() across frames) + double-invocation fix: added a resumable per-stage/per-chunk state machine (`WarmUpStep(left, right, map, msBudget)`, `CancelWarmUp()`, `WarmStage` enum, `m_Warm*` fields) so a Timeline mixer can spread the GPU upload + chunk-bounds computation across multiple frames while a preceding static clip plays, instead of paying the full cost synchronously at OnEnable(). Enforced hard guard: WarmUpStep no-ops (and cancels) if `enabled == true`, since Upload/BuildIndexBuffer/AllocateOutputBuffers write into the SAME fields the live/active pair uses — running warm-up while enabled would corrupt on-screen state. OnEnable() and SetAssets() both check for and consume matching completed warm state (BindBuffersForT only, skipping Setup()) instead of redoing the full synchronous rebuild.
[F] Real bug found and fixed during this work, worth carrying over precisely: SetAssets() and OnEnable() BOTH run for the same pair-change activation in the actual call pattern (SetAssets() called directly in C# by a mixer's ApplyMorphPair, then OnEnable() fires when Unity processes `enabled=true` moments later in the same call) — not one-or-the-other. Each independently checking/consuming warm state caused a race: whichever ran first consumed/cleared the warm state, then whichever ran second found nothing left and redid the full Setup() anyway, silently defeating the whole optimization while APPEARING correct in isolated code review. Fixed via a new `m_BoundThisActivation` bool: set true by whichever of SetAssets()/OnEnable() does the actual binding work first for a given activation; checked by whichever runs second, which then returns immediately without calling Setup() at all.
- A third Setup()/ReleaseGpuResources() call site exists in `SwapAssets()` — NOT given the same warm-consumption/double-invocation treatment, since the consuming project's Timeline mixer never calls SwapAssets() (confirmed via audit). Worth applying the same pattern there too if SwapAssets() is ever wired up to a caller that could race with warm-up, but left alone for now as genuinely out of scope.
