## What

`GaussianSplatMask` — a ScriptableObject storing an ordered list of named brush selections, each a snapshot of `m_GpuEditSelected` (sparse `int[] splatIndices`) paired with a float `weight` in [0,1]. A per-splat reveal system driven by a single `m_MaskT` parameter on the renderer. Not `GaussianCutout` (baked layer-range cutouts at import time). `GaussianSplatMask` is a **sub-asset of its target `GaussianSplatAsset`** (not a standalone `.asset` file) — one mask per splat asset, created via a "Create Mask" button in `GaussianSplatRendererEditor`'s Mask section (next to `m_Mask`, `m_MaskT` slider, keyframe dots).

## Why

The existing cutout system can't express free painted selections. The mask system enables animated progressive reveals: paint a selection, store it as a keyframe at a given weight, repeat. Timeline animates `m_MaskT`; the reveal curve emerges from all entries together. Vertex-stage application: mask weight multiplies `o.col.a`, NaN-culls below threshold — zero GPU fragment cost for masked-out splats.

A mask's `splatIndices` are meaningless without the specific `GaussianSplatAsset` they were painted against — coupling the mask as a sub-asset (rather than an independently-creatable standalone asset) prevents orphaned/mismatched masks and removes a manual two-step (create mask asset, then assign it) in favor of one button. The `[CreateAssetMenu]` standalone-creation path was removed entirely so there's no way to create a mask that isn't attached to an asset.

`splatIndices` is stored as raw bytes in a hidden `GaussianSplatMaskData` sub-asset rather than inline in the ScriptableObject, to avoid a full AssetDatabase reimport stall on every entry mutation at large splat counts. Lazy-loaded via a property reading `dataAsset.bytes` on first access after `OnAfterDeserialize` invalidates the cache (eager decode caused a load-order race).

`UpdateMaskBuffer` runs only when dirty; `SetMaskDirty` is deferred via `EditorApplication.delayCall` so it fires after `AssetDatabase.SaveAssets()` settles.

When a `GaussianSplatRenderer` has a mask assigned AND `m_MaskT == 0` at `OnEnable()` (i.e. it's authored to start fully hidden), its GPU resource init (buffer uploads, texture creation, sort-buffer setup) is deferred and spread across multiple frames via a time-budgeted coroutine (`UpdateRessourcesBudgeted()`) instead of paid synchronously in one — the splat isn't visible yet, so there's no urgency for its expensive first-frame init to complete immediately. A public `IsReady` bool reports readiness (`false` during the deferred load, `true` once complete) for external code — e.g. a Timeline gate — to check before starting to animate `m_MaskT` upward, avoiding a visual snap from stale/half-loaded state. Every other case (no mask, or `MaskT > 0` at `OnEnable`) keeps the original fully-synchronous `UpdateRessources()` path unchanged, `IsReady = true` immediately.

- **(2026-08-06) Mask-startup timing — RESOLVED.** Origin: cross-Project finding from KitchenOfMemories_Unity6's `performance` target, 2026-08-04 — Kenya memory scene's `Scene_Far/Hills_HQ/*_hq` `GaussianSplatRenderer`s had a correctly-assigned mask and correct `m_MaskT: 0` at scene-load pause, but showed hard-edged black cutout patches instead of full suppression, ~90% confidence attributed to the first-frame GPU init lag already profiled there (`Semaphore.WaitForSignal`/`Texture.AwakeFromLoad`/`Compute.Dispatch`). Confirmed via direct source read: `m_MaskT` is readable at `OnEnable()` before any GPU work runs; the mask itself is only touched later, separately, in `Update()` — no ordering constraint blocked a gating fix. User proposed the unifying design: defer the splat's GPU init entirely while mask-hidden (trigger: mask assigned + `MaskT==0` at `OnEnable`), gate rendering (not just loading) until resources are ready, end condition is "resources fully loaded" (not a frame count or MaskT change), decoupling load-completion from mask-value response. Implemented as `IsReady` (public bool) + `UpdateRessourcesBudgeted()` (time-budgeted coroutine, same pattern as KitchenOfMemories_Unity6's `SceneRenderVisibilityToggle`/MLS batching), wired into `Initialize()`'s `OnEnable` call path only (other `UpdateRessources()` callers — `LoadFromRuntimeData`, `SetAssets` — left untouched, smaller-scope-first). Hit and fixed a real `CS0104` compile error (`using System.Diagnostics;` ambiguating `UnityEngine.Debug`) — fixed by dropping the import and fully-qualifying the one `Stopwatch` use site. Live Play Mode repro confirmed the load genuinely spreads across 7 distinct frames (one yield per expensive call — layer-data copy, 3× `SetData`, `CreateColorTexture`, chunk buffer, sort-buffer init), `IsReady` correctly gates until complete. An apparent post-load rendering regression (splat not showing at `MaskT>0`) turned out to be a false alarm (camera framing during the test, not a bug). Found and fixed a real correctness gap during investigation: `m_PrevAsset`/`m_PrevHash` are normally set as a side effect of the synchronous `CreateResourcesForAsset()` call, which the budgeted path bypasses — without setting them explicitly, `Update()`'s first tick after `OnEnable` would see the asset as still "changed" and re-trigger a second, redundant synchronous load racing the coroutine. Fixed by setting both fields at the start of `UpdateRessourcesBudgeted()` too.
